# ТЗ: сервис записи на занятия к репетитору

REST API, через который ученики смотрят свободные слоты и записываются, а репетитор управляет расписанием. Сервис напоминает о занятиях и принимает заявки через вебхук. В будущем на API садится Telegram-бот.

Цель проекта: портфолио-проект, на котором можно показать проектирование REST API, работу с конкурентностью, кешированием, фоновыми задачами и инфраструктурой.

---

## 1. Стек

| Компонент | Технология |
|---|---|
| API | FastAPI (async) |
| БД | PostgreSQL + SQLAlchemy 2.x (async) + Alembic |
| Кеш, блокировки, лимиты | Redis |
| Фоновые задачи | arq (или Celery с брокером Redis) |
| Авторизация | JWT (access + refresh), роли `tutor` и `student` |
| Тесты | pytest, pytest-asyncio, httpx.AsyncClient |
| Инфраструктура | Docker, docker compose, GitHub Actions |
| Документация | Swagger / OpenAPI (автоматически из FastAPI) |

## 2. Роли и права

**Репетитор (`tutor`)**
- создаёт, изменяет, удаляет свои слоты;
- видит все брони на свои слоты и данные учеников, которые к нему записаны;
- отмечает оплату;
- обрабатывает заявки, пришедшие через вебхук.

**Ученик (`student`)**
- смотрит свободные слоты;
- бронирует слот и отменяет свою бронь;
- видит только свои брони и оплаты.

Доступ к чужому ресурсу → `403 Forbidden`. Нет токена или он невалиден → `401 Unauthorized`.

---

## 3. Модель данных

### users
- `id`, `email` (unique), `password_hash`, `role` (`tutor` | `student`), `created_at`

### students
- `id`, `user_id` (FK → users), `name`, `phone`, `telegram_id` (nullable, на будущее для бота)

### slots
- `id`, `tutor_id` (FK → users), `starts_at`, `ends_at`, `created_at`, `updated_at`
- Ограничение: `ends_at > starts_at`
- Слоты одного репетитора не пересекаются (exclusion constraint по `tstzrange` или проверка в сервисном слое)

### bookings
- `id`, `slot_id` (FK → slots), `student_id` (FK → students), `status` (`active` | `cancelled`), `reminded_at` (nullable), `created_at`, `cancelled_at`
- **Частичный уникальный индекс:** `UNIQUE (slot_id) WHERE status = 'active'`. Это главная защита от двойного бронирования, см. раздел 5.1

### payments
- `id`, `booking_id` (FK → bookings, unique), `amount`, `status` (`pending` | `paid`), `paid_at`, `source` (`manual` | `webhook`)

### webhook_requests (заявки)
- `id`, `external_id` (unique), `payload` (JSONB), `status` (`new` | `processed` | `rejected`), `created_at`

Все изменения схемы только через миграции Alembic.

## 4. REST API

Префикс: `/api/v1`. Формат: JSON. Время в ISO 8601 с часовым поясом, в БД хранится в UTC.

### 4.1 Авторизация
| Метод | Путь | Описание | Коды |
|---|---|---|---|
| POST | `/auth/register` | регистрация ученика | 201, 409 (email занят), 422 |
| POST | `/auth/login` | получение пары токенов | 200, 401, 429 |
| POST | `/auth/refresh` | обновление access-токена | 200, 401 |

### 4.2 Ученики
| Метод | Путь | Описание | Кто | Коды |
|---|---|---|---|---|
| GET | `/students` | список учеников с пагинацией | tutor | 200 |
| GET | `/students/{id}` | карточка ученика | tutor, сам ученик | 200, 403, 404 |
| GET | `/students/me` | свой профиль | student | 200 |
| PATCH | `/students/me` | изменить профиль | student | 200, 422 |

### 4.3 Слоты
| Метод | Путь | Описание | Кто | Коды |
|---|---|---|---|---|
| GET | `/slots` | список с фильтрами | все | 200 |
| GET | `/slots/{id}` | один слот | все | 200, 404 |
| POST | `/slots` | создать слот | tutor | 201, 409 (пересечение), 422 |
| PATCH | `/slots/{id}` | изменить | tutor-владелец | 200, 403, 404, 409 |
| DELETE | `/slots/{id}` | удалить | tutor-владелец | 204, 403, 404, 409 (есть активная бронь) |

Фильтры `GET /slots`: `date=2026-10-15`, `date_from`, `date_to`, `free=true`, `tutor_id`.

### 4.4 Бронирования
| Метод | Путь | Описание | Кто | Коды |
|---|---|---|---|---|
| POST | `/bookings` | забронировать слот (`{"slot_id": ...}`) | student | 201, 404, 409 (слот занят), 422 (слот в прошлом) |
| GET | `/bookings` | свои брони (ученик) или брони на свои слоты (репетитор) | все | 200 |
| GET | `/bookings/{id}` | одна бронь | участник брони | 200, 403, 404 |
| POST | `/bookings/{id}/cancel` | отменить | участник брони | 200, 403, 404, 409 (уже отменена) |

### 4.5 Оплаты
| Метод | Путь | Описание | Кто | Коды |
|---|---|---|---|---|
| GET | `/payments` | список | tutor — все свои, student — свои | 200 |
| POST | `/payments/{booking_id}/mark-paid` | отметить оплату вручную | tutor | 200, 403, 404, 409 |

Реальная платёжная система вне объёма проекта. Оплата отмечается вручную или через вебхук.

### 4.6 Вебхук
| Метод | Путь | Описание | Коды |
|---|---|---|---|
| POST | `/webhooks/requests` | приём заявки от внешней системы | 202, 401 (подпись), 200 (дубль), 429 |

- Подпись: заголовок `X-Signature` = HMAC-SHA256 тела запроса по общему секрету; сравнение через `hmac.compare_digest`.
- Идемпотентность: `external_id` из тела, см. раздел 5.5.

### 4.7 Общие требования к API
- **Пагинация:** `limit` (по умолчанию 20, максимум 100) и `offset`. Ответ: `{"items": [...], "total": N, "limit": ..., "offset": ...}`.
- **Ошибки** в едином формате: `{"error": {"code": "slot_already_booked", "message": "..."}}`.
- **Документация:** Swagger на `/docs`, у каждого эндпоинта описаны схемы ответов, включая ошибки.
- **Health-check:** `GET /health` проверяет связь с PostgreSQL и Redis.

## 5. Redis: применения

### 5.1 Блокировка при конкурентном бронировании
**Проблема:** два ученика одновременно бронируют один слот.

**Решение в два уровня:**
1. **Redis-блокировка (быстрый отсев).** `SET lock:slot:{id} <token> NX EX 10`, где `token` — случайный UUID. Не получили блокировку → сразу 409, в базу не идём.
2. **Ограничение в БД (источник истины).** Частичный уникальный индекс на `bookings(slot_id) WHERE status = 'active'`. `IntegrityError` при вставке → 409.

**Снятие блокировки:** только своей, через Lua-скрипт «удали, если значение равно моему токену». Иначе запрос, превысивший TTL, снимет чужую блокировку.

**Почему нужны оба уровня:** Redis может быть недоступен или TTL может истечь посреди транзакции; ограничение в БД гарантирует корректность в любом случае. Redis снимает нагрузку с базы при массовых конкурентных запросах.

### 5.2 Кеш расписания
**Проблема:** слоты запрашивают часто, меняются они редко.

**Решение:**
- Кешируется ответ `GET /slots`; ключ строится из параметров запроса и версии расписания: `slots:v{version}:tutor={id}:date=...:free=...`.
- Версия хранится в `schedule_version:{tutor_id}` и увеличивается через `INCR` при любом изменении слотов или броней этого репетитора.
- Старые ключи не удаляются явно, а истекают по TTL (например, 5 минут).

**Почему так:** не нужно перечислять и удалять все варианты ключей с разными фильтрами; инвалидация — одна атомарная операция.

### 5.3 Rate limiting
**Проблема:** перебор паролей на `/auth/login`, флуд на вебхук.

**Решение:** счётчик `INCR rl:{endpoint}:{ip или ключ}` + `EXPIRE` при первом инкременте (в одном pipeline или Lua-скрипте). Превышение → `429 Too Many Requests` с заголовком `Retry-After`.

Лимиты (настраиваются через env): логин — 5 попыток в минуту на IP+email, вебхук — 60 запросов в минуту на источник.

**Известное ограничение:** фиксированное окно допускает до 2× запросов на стыке окон. Альтернатива — sliding window на sorted set (`ZADD` + `ZREMRANGEBYSCORE`); описать в README как возможное улучшение.

### 5.4 Напоминания о занятиях (фоновые задачи)
**Проблема:** напомнить ученику за час до занятия, не блокируя HTTP-запрос.

**Решение:** воркер arq с периодической задачей раз в 5 минут:
- выбирает активные брони, где `starts_at` в ближайшие 60 минут и `reminded_at IS NULL`;
- отправляет напоминание (на этапе MVP — запись в лог / заглушка-нотификатор; позже — Telegram);
- проставляет `reminded_at`.

**Почему периодическая задача, а не отложенная на каждую бронь:** отмена и перенос брони не требуют удалять задачу из очереди, а рестарт воркера ничего не теряет. Повторная отправка исключена флагом `reminded_at` (обновление через `UPDATE ... WHERE reminded_at IS NULL`).

### 5.5 Идемпотентность вебхука
**Проблема:** внешняя система может доставить одну заявку несколько раз.

**Решение:** `SET webhook:{external_id} 1 NX EX 86400`. Ключ уже есть → отвечаем 200 и ничего не создаём. Дополнительно `external_id` уникален в таблице `webhook_requests`.

## 6. Нефункциональные требования
- `docker compose up` поднимает API, PostgreSQL, Redis и воркер; миграции применяются при старте.
- Конфигурация только через переменные окружения (pydantic-settings), в репозитории `.env.example`.
- Секреты (JWT, HMAC) не хранятся в коде.
- Пароли хешируются (bcrypt или argon2).
- Структурированные логи (JSON) с request id.
- Линтер и форматтер: ruff; типизация: mypy (желательно).

---

## 7. Тестирование
- pytest + pytest-asyncio, тесты идут против настоящих PostgreSQL и Redis (без моков для этих компонентов).
- **Обязательный тест на гонку:** 10–20 одновременных запросов `POST /bookings` на один слот через `asyncio.gather`; проверяется, что ровно один ответ `201`, остальные `409`, и в БД ровно одна активная бронь.
- Тест на сценарий без Redis-блокировки: ограничение в БД всё равно не даёт создать вторую бронь.
- Тесты прав: ученик не видит чужие брони (403), ученик не может создать слот (403).
- Тесты кеша: после изменения слота `GET /slots` возвращает актуальные данные.
- Тест rate limiting: N+1-й запрос получает 429.
- Тест вебхука: неверная подпись → 401, повторная доставка не создаёт дубль.
- Тест напоминаний: задача отмечает только подходящие брони и не шлёт повторно.
